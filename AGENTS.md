# AGENTS.md — MopedGame Agent Engineering Handbook

Read this file before inspecting code, proposing changes, or creating tasks. It defines the non-negotiable architectural boundaries, verification gates, repository layout, and multi-agent coordination rules for **MopedGame** (a stylized SF/Oakland Bay Area 2-stroke moped riding, wrenching, and garage simulator built with **Unity 6 LTS (URP, C#)**, a headless **.NET `MopedSim.Core`** kernel, and a **Blender CLI `.glb`** asset pipeline).

## 2. Golden Rules (Non-Negotiable)

1. **Strict Separation of Concerns (`MopedSim.Core` & `MopedSim.Data` are Engine-Agnostic)**
   - `MopedSim.Core` and `MopedSim.Data` MUST set `"noEngineReferences": true` in their `.asmdef` files and MUST NEVER import `UnityEngine` or `UnityEditor`.
   - Unity presentation assemblies (`MopedSim.Ride`, `MopedSim.Garage`, `MopedSim.World`, `MopedSim.UI`, `MopedSim.Audio`, `MopedSim.App`) MUST NEVER embed combustion math, AFR/CHT calculations, wrenching preconditions, fault triggers, or economy formulas. Unity scripts read `EngineTelemetrySnapshot` / `BikeState` and dispatch commands (`RideInputState`, `WrenchActionRequest`) into `MopedSim.Core`.
2. **Pin `netstandard2.1` + `LangVersion 9.0` + Warnings as Errors**
   - Every pure-C# `.csproj` under `src/` and `tests/` MUST target `netstandard2.1` (or `net8.0` for test runners referencing `netstandard2.1` libs) with `<LangVersion>9.0</LangVersion>`, `<Nullable>enable</Nullable>`, and `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>`.
   - Never use C# 10+ syntax (file-scoped namespaces, global usings, `required`, primary constructors on classes, collection expressions `[]`) inside shared `src/` packages, because Unity 6's C# compiler enforces C# 9.0 compatibility.
3. **Data-Driven Over Hardcoded**
   - All chassis archetypes, engine parts, carb jets, exhaust curves, fasteners, fault rules, garage upgrades, shops, deliveries, and Bay Area map zones belong in schema-validated JSON catalogs under `data/catalogs/`.
   - Never hardcode part stats, torque specs, or prices inside C# switch statements.
4. **Modular Additive Scenes & Zero Scene Merge Conflicts**
   - Never pile unrelated gameplay features into one monolithic `.unity` scene.
   - Keep `Bootstrap.unity`, `Garage.unity`, `UI_Overlay.unity`, and per-neighborhood additive zone scenes (`Zone_WestOakland.unity`, `Zone_OaklandHills.unity`, `Zone_BayCrossing.unity`, `Zone_SF_Mission.unity`) separated. Compose runtime objects via code/registries and scriptable builders (`MopedSim.Editor`) rather than manual scene hand-wiring.
5. **Headless Blender CLI & `SOCKET_*` Asset Contract**
   - All 3D moped parts, garage props, and modular environment kits MUST be generated by reproducible headless Python scripts in `tools/blender/` (`blender --background --python ...`) and exported as `.glb` (glTF 2.0, `export_yup=True`, metric `1 unit = 1 m`, scale `(1, 1, 1)`).
   - Every mechanical part requiring child attachments or fasteners MUST include exact `SOCKET_*` / `BOLT_*` empties matching `data/catalogs/parts.json`, verified by `tools/validators/validate_assets.py`.
6. **Determinism & Versioned Persistence**
   - `MopedSim.Core` simulation ticks MUST take explicit `float dt` and use injected `ISimRandom` (no `System.Random` static singletons, no `DateTime.Now`, no `UnityEngine.Time.deltaTime` inside core logic).
   - Save files MUST carry `schemaVersion` and an explicit migration path in `MopedSim.Data`.
7. **No Unverified Claims**
   - Never claim a task, bugfix, or milestone is complete based on reading code alone or saying "looks good." Every change MUST pass all applicable verification gates listed in Section 4, and you MUST report only directly observed command outputs.

## 4. Verification Gates Command Reference

Run every applicable gate after making changes. See [docs/PROJECT_GUIDE.md](docs/PROJECT_GUIDE.md) Section 6 for full gate specifications.

| Gate | Scope | Command (once M0+ is scaffolded) | Blocks Merge On |
| :--- | :--- | :--- | :--- |
| **Gate 1: Headless Core & Data Tests** | `MopedSim.Core`, `MopedSim.Data`, determinism, thermal/AFR/DAG math | `dotnet test tests/MopedSim.Tests.sln --configuration Release` | Any compiler warning, test failure, or non-deterministic run |
| **Gate 2: Data, Boundary & Asset Validators** | JSON schema parity, `noEngineReferences` checks, `.glb` tri budgets & `SOCKET_*` transforms | `python3 tools/validators/validate_all.py` | Missing socket, over-budget mesh, invalid catalog ref, forbidden `using UnityEngine` in `src/` |
| **Gate 3: Unity EditMode Tests** | Prefab/socket binding, assembly compilation in Unity 6, scene integrity | `"$UNITY_BIN" -batchmode -nographics -projectPath unity -runTests -testPlatform EditMode -testResults "$PWD/logs/editmode.xml"` (never pass `-quit` with `-runTests`) | Compilation warning/error or failed EditMode test |
| **Gate 4: Unity PlayMode Scenario Tests** | Riding acceleration, hill climb + CHT overheat, wrenching DAG, save/reload roundtrip | `"$UNITY_BIN" -batchmode -nographics -projectPath unity -runTests -testPlatform PlayMode -testResults "$PWD/logs/playmode.xml"` (never pass `-quit` with `-runTests`) | Any scenario assertion failure or uncaught console error |
| **Gate 5: Build Smoke Check** | Standalone macOS `arm64` player build & clean boot exit check | `"$UNITY_BIN" -batchmode -nographics -projectPath unity -executeMethod MopedSim.Editor.CliBuild.BuildMacOSDev -quit` | Build error, missing shader/scene, or runtime exception on boot |
| **Unified Runner** | Runs Gates 1–2 (fast, <10s) or `--full` for Gates 1–5 | `./scripts/verify.sh [--full]` | Non-zero exit code from any gate |

## 5. Definition of Done (DoD) for Every Agent Task

Before marking any implementation task done:

- [ ] **Boundary Compliance**: Zero `UnityEngine`/`UnityEditor` references in `src/MopedSim.Core` or `src/MopedSim.Data`; zero simulation math in `unity/Assets/Scripts/`.
- [ ] **Compiler Strictness**: `dotnet build` / `dotnet test` compiles cleanly with C# 9.0, `netstandard2.1`, `<Nullable>enable</Nullable>`, and zero warnings.
- [ ] **Tests Added/Updated**: Every new mechanical rule, fault, wrenching precondition, or ride feature has deterministic unit tests (Gate 1) and, where UI/scene/physics are touched, PlayMode/EditMode coverage (Gates 3–4).
- [ ] **Data & Asset Validation**: All catalog edits and Blender `.glb` exports pass `python3 tools/validators/validate_all.py` (Gate 2).
- [ ] **Documentation Synced**:
  - New architectural patterns or dependency shifts → add an entry in [docs/ARCHITECTURE_DECISIONS.md](docs/ARCHITECTURE_DECISIONS.md).
  - System contract changes → update [docs/PROJECT_GUIDE.md](docs/PROJECT_GUIDE.md).
  - Milestone progress & verification evidence → update [docs/ROADMAP_STATUS.md](docs/ROADMAP_STATUS.md).
- [ ] **Clean Workspace**: No stray temporary files, unreferenced `.meta` orphans, or uncommitted debug hacks.

## 6. Multi-Agent Coordination Rules

Parallel agents work in **disjoint domain ownership lanes** to prevent merge conflicts in `.unity` scenes, `.csproj` files, and `data/catalogs/`:

| Agent Lane | Primary Owned Paths | Never Edits Without Handoff |
| :--- | :--- | :--- |
| **Core Sim Agent** | `src/MopedSim.Core/`, `src/MopedSim.Data/`, `tests/`, `data/` | `unity/Assets/Scenes/`, `tools/blender/` |
| **Ride & Audio Agent** | `unity/Assets/Scripts/MopedSim.Ride/`, `unity/Assets/Scripts/MopedSim.Audio/`, `unity/Assets/Tests/PlayMode/Ride*` | `src/MopedSim.Core/` internals (request API via Core lane), `Zone_*` scenes |
| **Garage & UI Agent** | `unity/Assets/Scripts/MopedSim.Garage/`, `unity/Assets/Scripts/MopedSim.UI/`, `Garage.unity`, `UI_Overlay.unity` | `Zone_*` scenes, `MopedSim.Core/` formulas |
| **World / Bay Area Agent** | `unity/Assets/Scripts/MopedSim.World/`, `unity/Assets/Scenes/Zone_*.unity` | `Garage.unity`, `MopedSim.Core/` |
| **Blender Asset Agent** | `tools/blender/`, `unity/Assets/Art/Models/`, `tools/validators/validate_assets.py` | C# gameplay scripts, `.unity` scenes |
| **QA / Integration Agent** | `scripts/verify.sh`, `tools/validators/`, `unity/Assets/Scripts/MopedSim.Editor/`, `unity/Assets/Tests/` | Feature business logic |

### Escalation & ADR Rule
If implementing a task requires changing a settled boundary (e.g., adding a package dependency, splitting a scene, or altering `SOCKET_*` naming):
1. Do **not** silently work around the rule.
2. Document the proposed change in [docs/ARCHITECTURE_DECISIONS.md](docs/ARCHITECTURE_DECISIONS.md) as `Proposed` and update affected contracts in [docs/PROJECT_GUIDE.md](docs/PROJECT_GUIDE.md) before modifying code across lanes.
